# Выкатка изменений на прод — ранбук (I-9)

Как перенести наработки из этого репозитория на боевой shiduh.org. Рассчитано на человека с доступом к серверу; знание NetCat не требуется, но команды выполнять вдумчиво.

> **Прод — это не git-репозиторий.** Снимок в репозитории (`shiduh.org/`) — выгрузка боевого сайта без `.git`. На проде истории коммитов нет. Поэтому выкатка — это перенос файлов + миграции БД + настройки, а не `git pull` (если только вы заранее не превратили webroot прода в git-клон — см. §7).

> **Никогда не запускайте dev-стенд против боевой БД.** Обратное тоже: не тяните боевые секреты в репозиторий. Выкатка идёт в одну сторону — с dev на прод.

## 0. Перед началом — обязательный бэкдап

```bash
# на проде, до любых изменений
mysqldump -u root -p shiduh_org > backup_$(date +%F_%H%M).sql
tar czf webroot_$(date +%F_%H%M).tar.gz /path/to/webroot   # без netcat_files (2.7 ГБ)
```

Без свежего дампа не выкатывать: миграции меняют схему, и откат «в никуда» невозможен.

## 1. Как устроен прод — три факта, определяющих порядок действий

**1. Компиляции шаблонов нет.** `.html`-файлы компонентов и макетов — это уже PHP, они подключаются через `include`. Скопировали файл — он подхватился (с поправкой на OPcache, см. §5). Никакой «сборки» не требуется.

**2. Шаблоны компонентов лежат на диске в ДВУХ копиях.** В каждой папке компонента есть `Class.html` (склейка `FormPrefix` + `RecordTemplate` + `FormSuffix` через маркеры-комментарии `<!-- FormPrefix -->…`) и те же куски отдельными файлами. Источник истины — **`Class.html`**: при первом обращении ядро сравнивает `md5(Class.html)` с сохранённым `Class.File_Hash` в БД, и если не совпало — **пересобирает `FormPrefix/RecordTemplate/FormSuffix` из `Class.html`, затирая прямые правки этих трёх файлов** (`netcat/system/templating/nc_tpl_parser.class.php`). Практический вывод — в §4.

**3. Вся новая логика — в обычных PHP-файлах.** `api/*.php`, `admin-*.php`, `migrations/*.php` в снимке прода отсутствовали — это всё добавлено нами. Они не завязаны на механизм шаблонов, копируются напрямую. Единственная тонкость — порядок из-за общих библиотек (§3).

## 3. Порядок выкатки файлов — атомарность из-за общих библиотек

Появились разделяемые библиотеки, которые подключаются из нескольких мест:
- `api/admin_lib.php` ← почти все эндпоинты и admin-экраны (9 потребителей)
- `api/cases_lib.php` ← `cases_save.php`, `admin-cases.php`, `ai_chat.php`, `ai_tools.php`
- `api/ai_client.php` ← `ai_chat.php`, `summary_*`, `scoring_lib.php`, `match_explain.php`
- `api/scoring_lib.php` ← `assessment_answer.php`, `ai_tools.php`
- `api/match_lib.php` ← `match_list.php`, `match_feedback.php`, `match_explain.php`

**Скопировать зависимый файл без свежей библиотеки = `require_once` не найдёт функцию = fatal 500 на живом эндпоинте.**

Поэтому: **выкатывайте весь набор файлов разом (rsync/архив целиком), а не по одному.** Если копируете вручную — сначала все библиотеки (`*_lib.php`, `ai_client.php`, `ai_tools.php`, `ai_sensitive_fields.php`), потом эндпоинты, admin-экраны и шаблоны. Между этими двумя шагами сайт консистентен: старые эндпоинты не знают про новые библиотеки, новые библиотеки никого не ломают.

```bash
# рекомендуемый способ — одним rsync, атомарно с точки зрения пользователя
rsync -a --delete-after \
  shiduh.org/api/ shiduh@prod:/path/webroot/api/
rsync -a shiduh.org/admin-cases.php shiduh.org/admin-mailing.php \
  shiduh.org/admin-ai-prompt.php shiduh@prod:/path/webroot/
rsync -a shiduh.org/netcat_template/ shiduh@prod:/path/webroot/netcat_template/
rsync -a shiduh.org/migrations/ shiduh@prod:/path/webroot/migrations/
```

> `--delete-after` в `api/` уместно (каталог целиком наш). В `netcat_template/` — **без `--delete`**: там тысячи штатных файлов NetCat.

## 4. Ловушка двойной копии шаблонов — как не потерять правки

Правило одно: **шаблоны выкатывайте комплектом (и `Class.html`, и его parts), никогда выборочно.**

Почему это безопасно в нашем случае. Мы правили согласованно: там, где менялся `Class.html` (204, 204/238, 204/206), одновременно менялись и его parts. При первом обращении на проде `md5` нового `Class.html` не совпадёт со старым `File_Hash`, ядро пересоберёт parts **из нового `Class.html`** и обновит хэш — parts станут равны нашим правкам. Ничего руками делать не надо.

Где менялся только `RecordTemplateFull.html` / `Settings.html` (213, 272, 274, 238-Settings) — эти файлы **не входят** в склейку `Class.html` (в маркерах только FormPrefix/RecordTemplate/FormSuffix), поэтому ядро их не трогает, они копируются напрямую.

Опасность возникает лишь если выкатить `RecordTemplate.html` (списковую строку — она В склейке) БЕЗ соответствующего `Class.html`: старый `Class.html` совпадёт с `File_Hash`, ядро parts не тронет — и правка подхватится… до первого редактирования компонента в админке, которое пересоберёт parts из устаревшего `Class.html` и откатит правку. Комплектная выкатка это исключает.

**Альтернатива для нетехнического деплоя** — внести правки шаблона через админку NetCat (Управление компонентами → шаблон → вставить код → сохранить): `parts2main` соберёт `Class.html` из parts и обновит `File_Hash` сам. Но при десятках файлов rsync-ом надёжнее.

## 5. Сброс кэшей после выкатки файлов

| Что тронули | Что сбросить |
|---|---|
| `.html` шаблон или `api/*.php` | OPcache: `revalidate_freq=2` подхватит через ~2 с; для мгновенного — `systemctl reload php-fpm` (или `opcache_reset()`) |
| Шаблон компонента (`Class.html`) | ничего — `File_Hash` пересчитывается автоматически при первом обращении (§4) |
| `Settings` (ниже) | читаются с параметром обновления кэша; надёжно — очистить кэш настроек в админке или перезагрузить админку |

Добавление полей через миграции (`add_field()`) кэш универсальных шаблонов обновляет само.

## 6. Миграции схемы

```bash
# на проде, ПОСЛЕ копирования каталога migrations/ и БЭКАПА БД
php migrations/migrate.php status   # что применено, что ждёт
php migrations/migrate.php up        # применить неприменённые (идемпотентно)
```

- `up` идемпотентен: уже применённые пропускаются, повторный запуск безопасен.
- **В нумерации осознанная дыра на `014`.** Набор `014_subscriptions` (монетизация Э4) был реализован и откачен — файла нет намеренно. Ожидаемый результат `status`: применены `001`–`013` и `015`–`020`, `014` отсутствует. **Не пытайтесь «восстановить» 014** — монетизация отложена заказчиком (см. ROADMAP Раздел VII).
- Откат: `php migrations/migrate.php down` (последняя) или `down-all` (все в обратном порядке). Каждый набор обратим.

## 7. Настройки БД (`Settings`, `Module='ai'`, `Catalogue_ID=0`)

Без ключа всё работает на безопасных заглушках (сайт исправен). Живой ИИ включается настройками — **правкой кода не требуется**:

| Ключ | Значение по умолчанию | Когда менять |
|---|---|---|
| `provider` | `stub` | `openrouter` — включить живой LLM |
| `api_key` | `''` | ключ OpenRouter (Э1) — **не хранить в git** |
| `base_url` | `https://openrouter.ai/api/v1` | если другой OpenAI-совместимый шлюз |
| `model` | `openai/gpt-4o-mini` | выбор модели |
| `temperature` | `0.7` | тон ответов |
| `timeout` | `15` | сек на запрос |
| `max_retries` | `2` | ретраи при 429/5xx |
| `rate_limit_per_hour` | `30` | лимит сообщений чата на пользователя |
| `rag_url` | `''` (RAG выкл.) | адрес RAG-сервиса (§8), напр. `http://127.0.0.1:8100` |
| `rag_top_k` | `3` | сколько фрагментов книг подставлять |
| `rag_timeout` | `3` | сек; **поднять, если RAG-сервис перешёл на openrouter-эмбеддинги** |

> При `provider=openrouter` + пустом `api_key` эндпоинты честно отвечают «ключ не задан», а не молчат. Пока `provider=stub` — чат отвечает заглушкой, скоринг/подбор/обоснования считаются кодом без обращения к сети.

## 8. RAG-сервис (опционально, Э2.1)

Отдельный Python-сервис отдаёт фрагменты книг для консультанта. Без него консультант работает как обычно, без подстановки фрагментов (`rag_url=''`).

```bash
cd rag && pip install -r requirements.txt
# индекс чанков уже в rag/data/chunks.jsonl (оффлайн-эмбеддер, без ключа)
uvicorn --factory rag.service.app:get_app --host 127.0.0.1 --port 8100
# проверка: curl 127.0.0.1:8100/health  → {"chunks": 1271, ...}
```

Затем в `Settings` задать `rag_url=http://127.0.0.1:8100`. Реальные эмбеддинги (точнее поиск) включаются переменными окружения сервиса `RAG_EMBEDDER=openrouter` + `OPENROUTER_API_KEY` — тогда **поднимите `rag_timeout`** (эмбеддинг запроса становится сетевым вызовом).

## 8.5. Окно для смены SecretKey и жёсткости сессий (B-3, B-4)

Две правки безопасности требуют аккуратного момента выкатки. Обе применяются
**миграциями** (`018_session_ip_binding`, `019_rotate_secret_key`) — отдельных
ручных действий в БД не нужно.

### Что меняется и что от этого ломается

| Правка | Что делает | Радиус поражения |
|---|---|---|
| `019` — ротация `SecretKey` | Заменяет `md5('')` на случайный ключ. Сейчас ключ общеизвестен, а токен = `md5(user_id + ключ)`, то есть валидный `nc_token` для любого пользователя вычисляется в одну строку | **Только формы, уже открытые в браузерах**: их отправка получит отказ, человеку надо обновить страницу. Сессии, пароли, письма и ссылки-приглашения НЕ затрагиваются. **Затрагиваются формы сообщений** (шаблоны 265/259/320): хэш настроек виджета фото зависит от ключа — выкатывать их вместе с миграцией, иначе любая отправка сообщения ответит «Settings integrity error» |
| `018` — привязка сессии к сети | `ip_check_level` 0 → 2 (первые два октета) | Пользователь, у которого адрес сменился за пределы /16 (обычно смена оператора/сети), будет разлогинен и войдёт заново |
| `vars.inc.php` — `ADMIN_AUTHTIME` | 365 суток → 30 суток | Кто не заходил больше 30 дней — войдёт заново. Окно скользящее: активных не разлогинивает |

Проверено на стенде (2026-09-02, тест `photo_message_test.py` 6/6): `settings_image_hash`
**зависит** от `SecretKey` (`nc_multifield_settings::get_setting_hash()` включает ключ), а в
шаблонах 265/259/320 и 183/275 (статьи) он был захардкожен под прод-ключ. Прежняя запись здесь была ошибочной:
тест подставлял вычисленный хэш и маскировал поломку. Теперь шаблоны печатают хэш динамически
(`$f_image->settings->get_setting_hash()`) — выкатывать их в одном окне с миграцией `019`.

### Порядок в окне

1. Выбрать час наименьшей активности (ночь по московскому времени).
2. Сделать бэкап (§0) — как перед любой выкаткой.
3. Выкатить файлы (§3), **не забыв `vars.inc.php`**: это не git-файл, значение
   `ADMIN_AUTHTIME` правится на сервере руками, ориентир — `vars.inc.php.example`.
4. `php migrations/migrate.php up` — применит `018` и `019`.
5. Проверить: открыть сайт, войти, отправить любую форму (например, правку
   анкеты). Если форма была открыта до ротации — обновить страницу.
6. Предупредить шадханов заранее: «в такое-то время возможен повторный вход».

### Если пошли жалобы

- **«Постоянно разлогинивает»** — виновата привязка к сети. Уровень снижается
  настройкой, без выкатки: админка → модуль «Авторизация» → `ip_check_level`,
  поставить `1` (первый октет) или `0` (выключить). Или откатить `018`.
- **«Форма не отправляется»** после ротации — обновить страницу. Если
  повторяется у всех и после обновления — откатывать не ключ, а смотреть логи:
  ротация на это влиять не может.

Откат `019` намеренно НЕ возвращает прежний ключ: вернуть общеизвестный
`md5('')` значило бы заново открыть дыру.

## 12. Логи ошибок (наблюдаемость)

До этапа «До идеала» `.htaccess` ставил `error_reporting 0` — фатал в шаблоне или эндпоинте
не оставлял следа нигде. Теперь в трёх блоках `mod_php` стоит `log_errors on` и
`error_reporting 22519` (`E_ALL & ~E_NOTICE & ~E_STRICT & ~E_DEPRECATED`), `display_errors off`.

**Куда пишется.** По умолчанию — в ErrorLog Apache (вне webroot, ротируется хостингом):
на VPS обычно `/var/log/apache2/error.log`, на виртуальном хостинге — каталог логов в панели
(на Beget — `~/logs/`). Если нужен отдельный файл, в конфиге vhost (не в `.htaccess`,
путь на каждом сервере свой): `php_value error_log /path/outside/webroot/php-error.log`.
На стенде: `docker compose logs -f web`.

**Что искать после выкатки.** Наш код пишет через `shiduh_log($channel, …)` с префиксом канала:

| Префикс | Что значит |
|---|---|
| `[fatal]` | необработанная фатальная ошибка в `api/*.php` (клиент получил JSON 500 «Внутренняя ошибка сервера») |
| `[ai]` | провайдер ИИ: таймауты, отказ по ключу, ретраи, промпт |
| `[match]` | подбор пар и обоснования (аудит: кто и что запрашивал) |
| `[rag]` | ретривер книг недоступен или отвечает не тем |
| `[scoring]` | профиль ценностей не сохранился |
| `PHP Fatal error` | фатал в шаблоне NetCat (вне `api/`) |

Полезная команда: `grep -E "\[(fatal|ai|rag)\]|PHP Fatal" error.log | tail -50`.

**Эндпоинты.** Каждый `api/*.php` вызывает `shiduh_bootstrap_api()` до загрузки ядра: фатал
внутри `include` теперь отдаёт JSON 500 без подробностей (раньше — пустой ответ 200 из-за
`ob_start()` ядра), подробности уходят в лог.
