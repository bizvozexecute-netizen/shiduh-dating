# ТЗ: Модернизация shiduh.org — внедрение ИИ-модулей

> **Для кого этот документ:** для ИИ-агента (Claude Code) и разработчика.
> **Как использовать:** выполнять фазы строго по порядку. Фаза A (аудит) обязательна перед любыми изменениями. Результаты фазы A фиксируются в `AUDIT.md` и определяют конкретные технические решения дальнейших этапов.

---

## 0. Контекст проекта

- **Продукт:** платформа еврейских знакомств через свах (шадханов). ~2000+ анкет кандидатов, живые шадханы.
- **Проблема:** анкеты заполнены неполно; подбор пар делается вручную.
- **Цель:** (1) дозаполнить анкеты через диалог с ИИ, (2) построить ценностный профиль кандидата, (3) дать шадхану ранжированные рекомендации пар с обоснованием, (4) подготовить задел под платный доступ.
- **Код передан заказчиком.** Стек заранее неизвестен — определяется в фазе A.

### Глобальные запреты (действуют на всех фазах)

1. **Никогда не работать с продакшен-базой и продакшен-сервером.** Вся разработка — локально на обезличенных данных.
2. **Не коммитить секреты** (ключи API, пароли, .env) в репозиторий.
3. **Все изменения схемы БД — только через обратимые миграции** (每 миграция имеет down/rollback).
4. **Не переписывать существующий работающий код без необходимости.** Встраиваемся в текущую архитектуру, рефакторим только то, что блокирует задачу.
5. **Реальные ПД (имена, телефоны, email, переписка) не должны попадать** в логи, тесты, фикстуры и промпты, отправляемые внешним LLM-провайдерам.
6. Каждая фаза завершается работающим состоянием: код собирается, тесты проходят, есть краткий отчёт что сделано.

- Mobile-first: интерфейс полноценно работает на смартфоне.
- Дизайн — минималистичный, в стилистике текущего сайта.
- На этой фазе чат может отвечать заглушкой «ИИ подключается на следующем этапе» — интерфейс и хранение сообщений должны работать полностью.

- Шадхан НЕ видит переписку кандидата с ИИ — только резюме.

## Фаза Э1. ИИ-консультант: диалог и автозаполнение анкеты

### Э1.1. Слой интеграции с LLM (провайдер-абстракция)

- Создать модуль `LLMClient` с интерфейсом: `chat(messages, tools?, options) -> {content, tool_calls, usage}`.
- Реализации-адаптеры: OpenAI-совместимый API (gpt-4o-mini) — первый; конструкция должна позволять добавить YandexGPT/GigaChat без изменения бизнес-логики.
- Провайдер, ключи, base_url — из конфигурации окружения. **Ключи не в коде.**
- Обработка ошибок: таймаут, ретрай с бэкоффом (макс. 2), понятное сообщение пользователю при недоступности.
- Учёт токенов: сохранять `usage` в `ai_chat_messages.tokens_used`.

### Э1.2. Системный промпт из админки

- Промпт роли консультанта хранится в `ai_prompts` (key = `consultant_system`), редактируется в админ-панели.
- Стартовое содержимое: «Ты — мудрый, вежливый ИИ-консультант еврейской платформы. Твоя цель — помочь заполнить анкету. Общайся уважительно, используй понятную терминологию (Шаббат, кашрут, хупа, мицва). Не задавай вопросы списком — веди живой диалог.»
- При сохранении — новая версия (старая остаётся в истории), возможность отката.

### Э1.3. Автозаполнение через tool calling

Определить инструмент (function calling) `update_profile_fields`:

```json
{
  "name": "update_profile_fields",
  "description": "Записать распознанные из беседы данные анкеты",
  "parameters": {
    "location": "string", "origin": "string",
    "kashrut_level": "none|basic|traditional|strict",
    "shabbat_level": "none|partial|traditional|strict",
    "family_values": {"budget": "...", "roles": "...", "children": "...", "parents": "..."},
    "relocation_ready": "boolean",
    "relocation_cities": ["string"]
  }
}
```

**Конвейер обработки вызова (строго в этом порядке):**
1. LLM возвращает tool_call с распознанными полями.
2. Бэкенд-валидация: каждое значение проверяется по словарю допустимых. Невалидное — отбрасывается (не «чинится» молча).
3. Политика записи: **записываем только пустые поля.** Если поле уже заполнено и LLM предлагает другое значение — НЕ перезаписывать; ИИ в диалоге уточняет у пользователя («У тебя указано X, поменять на Y?»), перезапись только после явного подтверждения.
4. Каждая запись — строка в `ai_field_writes`.
5. После записи ИИ продолжает диалог естественно (не рапортует «данные сохранены в базу», а ведёт беседу).

### Э1.4. Генерация ai_summary

- По команде (кнопка шадхана «Обновить резюме») или автоматически после N новых сообщений: LLM получает анкету + последние сообщения диалога → генерирует резюме характера в 3–6 предложений → сохраняется в `ai_summary` + `ai_summary_meta`.
- В промпт для внешнего LLM не передавать прямые идентификаторы (фамилия, телефон, email).

**Критерии готовности Э1:** живой диалог работает; свободный текст «вырос в Махачкале, живу в Москве, едим кошерное» приводит к корректной записи `origin/location/kashrut_level`; заполненные поля не перетираются без подтверждения; лог `ai_field_writes` ведётся; резюме генерируется.

## Фаза Э2. Ценностный профиль (RAG + детерминированный скоринг)

### Э2.1. RAG-база по книгам

- Вход: 3 книги (2 — психология отношений, 1 — еврейские устои). Формат: PDF/EPUB/TXT — уточнить у заказчика.
- Конвейер индексации (offline-скрипт): парсинг → чистка → нарезка на чанки (~500–800 токенов с перекрытием ~100) → эмбеддинги (та же модель, что в Э3) → сохранение в таблицу `rag_chunks`: `id, book, chapter_hint, content, embedding`.
- Ретривер: по запросу — top-k (k=4–6) чанков по косинусному сходству.
- Использование: найденные чанки подставляются в промпт консультанта с инструкцией «Отвечай, опираясь только на приведённые фрагменты. Если фрагменты не отвечают на вопрос — скажи об этом, не выдумывай.»
- Пользователю НЕ выводятся дословные цитаты книг длиннее пары строк — пересказ своими словами (юридическое требование).

### Э2.2. Кейсы и опрос в диалоге

- Таблица `assessment_cases`: `id, dimension (love_language_* | family_*), scenario_text, active, order`. Кейсы редактируются в админке.
- Покрытие: **5–7 кейсов на каждое измеряемое измерение.** Языки любви: 5 измерений (слова, время, подарки, забота, прикосновения). Семейные ценности: бюджет, воспитание, отношения с родителями (по словарям из Э0).
- ИИ вплетает кейсы в диалог (не «вопрос 1/2/3»), по одному, дожидаясь ответа.

### Э2.3. Скоринг: детерминированный, воспроизводимый

- Роль LLM — **только классификация одного ответа**: `classify_case_answer(case, answer) -> {dimension_scores: {любовь_время: 0..2, ...}, confidence}` (structured output, температура 0).
- Итоговый профиль считает **код, не LLM**: суммирование баллов по измерениям → нормировка в проценты.
- Схема `psychological_profile`:

```json
{
  "love_languages": {"words": 0.30, "time": 0.40, "gifts": 0.05, "service": 0.15, "touch": 0.10},
  "family_values_scores": {"budget": "...", "children": "...", "parents": "..."},
  "completed_at": "ISO-8601",
  "cases_answered": 27,
  "version": 1
}
```

- **Фиксация результата:** после завершения опроса профиль записывается и НЕ пересчитывается при просмотрах. Повторное прохождение — только явной командой, создаёт новую версию.
- Текстовое описание психотипа: генерируется LLM один раз по готовым цифрам, кэшируется в профиле.

### Э2.4. Визуализация у шадхана

- В карточке кандидата: radar/bar-диаграмма языков любви (Chart.js или иная библиотека, уже используемая в проекте) + текст психотипа.
- Данные — из `psychological_profile`. Если профиль не заполнен — заглушка «Тест не пройден».

**Критерии готовности Э2:** индексация книг работает; ответы ИИ по темам отношений опираются на чанки книг; повторное прохождение тем же набором ответов даёт тот же профиль (детерминизм); диаграмма отображается.

## Фаза Э3. Подбор пар (гибридный matching)

### Э3.1. Слой 1 — жёсткие фильтры (SQL)

Кандидаты в пару обязаны пройти ВСЕ фильтры:
- Противоположный пол.
- Возраст **асимметрично**: возраст Б входит в допустимый диапазон А, И возраст А входит в диапазон Б (поля диапазонов — добавить в анкету, если их нет; дефолт вычислять консервативно).
- Религиозная совместимость по **матрице**, а не равенству. Матрицы для `kashrut_level` и `shabbat_level` хранятся в конфиге/справочной таблице, заполняются заказчиком (раввином). Дефолт до получения: совместимы соседние уровни, несовместимы крайние (`none` × `strict`).
- География: один город, ИЛИ у одной из сторон `relocation_ready=true` и город второй стороны входит в её `relocation_cities`.

Выход слоя — список допустимых пар. Реализация — индексированный SQL-запрос.

### Э3.2. Слой 2 — ранжирование

Для каждой допустимой пары итоговый балл:

```
score = w1 * values_match + w2 * love_language_match + w3 * semantic_similarity
(дефолт: w1=0.4, w2=0.3, w3=0.3; веса — в конфиге)
```

- `values_match`: доля совпадений по `family_values` (правила сравнения по словарям).
- `love_language_match`: косинусная близость векторов языков любви из профилей.
- `semantic_similarity`: косинус эмбеддингов **свободного текста** анкет («о себе», «кого ищу») — НЕ всей анкеты.
- Эмбеддинги: считаются один раз при изменении текста анкеты (проверка по `source_hash`), хранятся в `profile_embedding`. Модель — text-embedding-3-small или аналог провайдера. Для 2000 анкет отдельная векторная БД НЕ нужна: косинус в приложении/SQL. Если СУБД — PostgreSQL и pgvector доступен, можно использовать его, но это не требование.
- Пересчёт рекомендаций — фоновой задачей (ночной cron) + кнопка ручного пересчёта у шадхана.

### Э3.3. Экран «Рекомендации ИИ» у шадхана

- Список пар по убыванию балла: «Давид (26, Москва) × Сарра (23, Пятигорск) — 87%». Процент = итоговый score.
- Клик по паре → LLM генерирует обоснование ИЗ уже посчитанной разбивки score (в промпт передаются компоненты балла и совпавшие поля): «Оба ориентированы на традиционную семью, языки любви совпадают (время вместе), оба готовы жить в Москве.» Обоснование кэшируется.
- Кнопки: «Предложить шидух» / «Отклонить». При отклонении — выбор причины из списка (возраст / география / религиозность / семьи не сойдутся / другое + комментарий).
- Таблица `match_feedback`: `id, shadchan_id, user_a, user_b, action, reason, comment, created_at`.
- Учёт отклонений: отклонённая пара исключается из выдачи этого шадхана; причина «религиозность/возраст» по возможности понижает вес соответствующего компонента в будущих подборах (простая эвристика, не ML).

**Критерии готовности Э3:** пары, не проходящие жёсткие фильтры, НИКОГДА не попадают в выдачу (покрыть тестами: однополая пара, `none`×`strict`, вне возрастных рамок); ранжирование воспроизводимо; обоснование ссылается только на реальные данные пары; фидбек сохраняется и влияет на выдачу.

## Порядок работ и определение готовности

1. Фаза A → `AUDIT.md`, локальный запуск. **Пауза: сверка плана с фактическим стеком.**
2. Э0 → миграции + интерфейсы (чат-заглушка, блок резюме).
3. Э1 → живой ИИ-консультант с автозаполнением.
4. Рассылка (малая задача, можно параллельно с Э1 после A).
5. Э2 → RAG + профиль.
6. Э3 → подбор.
7. Э4 → ограничение доступа.

Каждая фаза: код собирается, миграции обратимы, есть тесты на ключевую логику (валидация записей ИИ, фильтры подбора, детерминизм скоринга), краткий отчёт.

## Открытые вопросы (не блокируют A и Э0)

1. Матрицы религиозной совместимости — от раввина (до Э3).
2. Три книги в электронном виде — от заказчика (до Э2).
3. Выбор LLM-провайдера и владелец API-ключей (до Э1).
4. Формулировки кейсов (5–7 на измерение) — согласовать (до Э2).
5. Брендинг: shiduh.org vs Onesoul (до Э0.2 — влияет на тексты интерфейса).
